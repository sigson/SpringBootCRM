# Модуль `app.modules.dcs` — компоновка даних (аналог 1С:СКД)

Незалежний, **відключуваний** і **видаляється однією папкою** рушій звітів: схема
джерел → налаштування виводу → дерево підсумків із даними розшифровки, вивантаженням
у XLSX/CSV і розшифровкою.

Побудований за тими самими правилами ізоляції, що й `app.modules.sqlworkbench`, з
однією відмінністю: **потребує Workbench**, бо набори даних звіту — це його пакет
запитів.

## Що зберігає звіт

Схеми та налаштування живуть у довіднику хоста `app.springbootcrm.reports`
(typeId 9500) чотирма JSON-реквізитами:

| Реквізит | Що це |
|---|---|
| `scheme` | набори даних (упакований рядок), зв'язки, обчислювані поля, ресурси, параметри |
| `settings` | налаштування за замовчуванням + іменовані **варіанти звіту** |
| `templates` | макети областей виводу |
| `forms` | форми звіту, зібрані візуальним конструктором форм |

Хост тримає їх як непрозорі дерева (`JsonNodeConverter`): структуру знає і
інтерпретує тільки цей модуль та його конструктор на фронтенді. Тому модель
компоновки розвивається без міграцій, а видалення модуля лишає довідник живим —
просто звіти перестають формуватися.

## Конвеєр

```
налаштування за замовчуванням ⊕ варіант ⊕ користувацькі   SettingsComposer
        ↓
які поля взагалі потрібні (транзитивно через вирази)      UsageCollector
        ↓
схема + налаштування → один SQL                            LayoutComposer
   · набори з упакованого рядка                            (→ QueryPackCodec)
   · зв'язки → ланцюжок JOIN'ів поверх CTE                 (→ QueryPackAssembler)
   · відбір → WHERE з bind-параметрами
   · рішення «агрегувати в СУБД чи в процесорі»
        ↓
виконання (лише SELECT, PreparedStatement)                 QueryService (Workbench)
        ↓
рядки → дерево підсумків                                   CompositionProcessor
   · обчислювані та користувацькі поля
   · ресурси на кожному рівні групування
   · крос-таблиці, умовне оформлення, дані розшифровки
        ↓
CompositionResult → фронтенд / XLSX / CSV
```

### Два режими агрегації

`LayoutComposer` вмикає **агрегацію в СУБД** (`GROUP BY` за вимірами), коли
одночасно: усі ресурси — прості згортувані агрегати (`Сумма`, `Количество`,
`Минимум`, `Максимум`), у структурі немає детальних записів, у виводі немає
обчислюваних полів, а відбір цілком пішов у `WHERE`. Тоді процесору лишається
**згорнути** готові підсумки вгору по ієрархії (`Сумма(ресурс)`).

Інакше запит віддає детальні рядки, і все рахує процесор. Це завжди коректно, але
дорожче. Умови навмисно суворі: помилитися в бік «повільно, але правильно» тут
дешевше, ніж отримати неправильні підсумки.

`Среднее` і `КоличествоРазличных` згорнути за групами не можна — вони самі по собі
вимикають перший режим.

### Чому підсумки — це вираз, а не накопичення

Кожен рівень викликає обчислювач над **своєю множиною записів**. Тому ресурс виду
`Сумма(Продажи.Сумма) / Сумма(Продажи.Количество)` на підсумку дає правильне
значення, а не суму часткових — класичну помилку «нарощуваних» підсумків.

## Конструктор запиту набору даних

Набір даних — це звичайний SELECT, а візуальний конструктор для нього вже є в
Workbench'і. Тому у вкладці «Набори даних» монтується **той самий** компонент
(`StatementEditor` з `modules/sqlworkbench`), а не його копія: копія неминуче
розійшлася б з оригіналом — ссилковий режим, з'єднання, об'єднання та підзапити
довелося б підтримувати двічі.

Стикування точне у двох місцях:

* `statementToSql` віддає текст **без підстановки параметрів** (інлайном займається
  `buildExecutableSql`, він тут не потрібен). Тому `&Ім'я`, набране в умові
  конструктора, доїжджає до компоновника макета і зв'язується параметром схеми —
  синтаксис у обох однаковий;
* дерево конструктора зберігається в самому наборі (`dataSet.builder`), а в
  упакований рядок іде лише згенерований SQL. Рядок лишається читаним і здійсненним,
  а запит при цьому можна відкрити й правити далі мишею.

Правка SQL текстом відв'язує набір від конструктора: розібрати довільний SQL назад у
дерево не можна, і вдавати, що можна, було б гірше, ніж сказати прямо.

`ParameterBinder` — спільний прохід «`&Ім'я` → `?` + список значень». Текст набору
виконується не лише при компоновці: його ж запускають автозаповнення полів
(`/describe-datasets`) і попередній перегляд даних (`/preview-dataset`). Поки проходу
не було спільного, обидва ці шляхи падали на першому ж `&Параметрі`.

## Мова виразів

Власний інтерпретатор (`expression/`): лексер + рекурсивний спуск + обчислювач.
Числа — `BigDecimal` (грошові підсумки не мають накопичувати похибку `double`).

* агрегати: `Сумма`, `Количество`, `КоличествоРазличных`, `Минимум`, `Максимум`, `Среднее`;
* рівень групування: `ВычислитьВыражение(вираз, групування, область)` з областями
  `ОбщийИтог` / `Иерархия` / `Группировка`, `Уровень()`, `НомерПоПорядку()`;
* умови: `ВЫБОР КОГДА … ТОГДА … ИНАЧЕ … КОНЕЦ`, `И`/`ИЛИ`/`НЕ`, `В (…)`, `МЕЖДУ`,
  `ЕСТЬ NULL`, `ПОДОБНО`;
* рядки й дати: `Представление`, `Подстрока`, `СокрЛП`, `ВРег`, `НРег`, `Год`,
  `Квартал`, `Месяц`, `День`, `НачалоПериода`, `КонецПериода`, `Округл`, `ЕстьNULL`.

Імена приймаються російською та англійською, регістр не важливий. Невідома функція —
явна помилка, а не тихий `null`: мовчазний `null` перетворюється на неправильний
підсумок, який ніхто не помітить.

## Безпека

Жодне користувацьке значення не потрапляє в текст SQL. Значення відборів
підставляються маркерами `&_fN`, параметри схеми — своїми іменами `&Имя`; фінальний
прохід міняє всі маркери на `?` зліва направо і збирає значення в тому ж порядку.
Ін'єкція неможлива **за побудовою**, а не за дисципліною викликача.

Виконання йде через `QueryService` Workbench'а: він уже відхиляє будь-який
не-SELECT і працює з read-only датасорсом хоста. Власної політики доступу модуль не
заводить — права дає access-checked репозиторій довідника звітів.

## Межі поточної реалізації

Чесно перелічено те, що оголошено в ТЗ, але поки не зроблено:

* **Ієрархічні групування** (`Иерархия`, `Только иерархия`) будуються плоскими:
  схема не описує поля-батька. Процесор про це попереджає у `warnings`.
* **Макети** зберігаються й редагуються; на виводі застосовуються області
  «Шапка звіту» та «Підвал» (з підстановкою `[Поле]`). Області «Групування» та
  «Детальні записи» поки малює автоматичний вивід.
* **Залишки за ролями полів** (`beginBalance`/`endBalance` + порядок періодів) —
  ролі зберігаються в схемі, але окремого алгоритму залишків ще немає.
* **Доповнення періодів** і **вкладені схеми** не реалізовані.
* **Експорт у PDF** не реалізований (є XLSX і CSV, обидва без сторонніх бібліотек).

## API (база `/api/dcs`)

```
GET    /capabilities
POST   /reports/{id}/compose                 сформувати збережений звіт
POST   /reports/{id}/drilldown               розшифровка комірки
GET    /reports/{id}/available-fields        поля + параметри + варіанти + форми + макети
POST   /reports/{id}/export?format=xlsx|csv
POST   /compose                              схема й налаштування в тілі (конструктор)
POST   /preview-sql                          згенерований SQL без виконання
POST   /available-fields
POST   /describe-datasets                    автозаповнення полів набору
POST   /validate-expression
POST   /export?format=xlsx|csv
```

## API (база `/api/dcs`) — службові виклики конструктора

```
POST   /describe-datasets      колонки кожного набору (автозаповнення полів)
POST   /preview-dataset        дані одного набору (кнопка «Preview data»)
```
Обидва приймають `parameters` і виконують набір зі зв'язаними `&Параметрами`.

## Видалення

Видаліть теки `backend/src/main/java/app/modules/dcs` і
`backend/src/test/java/app/modules/dcs` (тести живуть у дзеркальному дереві й
видаляються разом із модулем), а на фронтенді — `frontend/src/modules/dcs`,
`frontend/src/editors/ReportEditor.tsx`, `frontend/src/editors/ReportRunnerWindow.tsx`,
`frontend/src/editors/reportActions.tsx` і два рядки в `editors/listViews.tsx`.

Довідник звітів (`app.springbootcrm.reports`) лишається робочим JSON-каталогом:
`app.springbootcrm` на модуль не посилається жодним рядком.

**Зворотний порядок — інший.** Видалення Workbench'а тепер ламає і компоновку: на
бекенді модуль збирає набори його пакетом запитів, а на фронтенді `DatasetQueryBuilder`
імпортує його конструктор. Це та сама однобічна залежність `dcs → sqlworkbench`, просто
тепер вона є і на фронтенді. Видаляти Workbench слід **після** компоновки, або разом із
`frontend/src/modules/dcs/DatasetQueryBuilder.tsx` та вкладкою «Конструктор», що на нього
посилається (вкладка «SQL» працює без нього).
