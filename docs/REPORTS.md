# Генератор отчётов (аналог 1С:СКД) и его связь с SQL Workbench

Справочник отчётов в хосте, движок компоновки
отдельным модулем и конструктор на фронтенде. Наборы данных отчёта — это **пакет
запросов SQL Workbench'а**: несколько запросов, упакованных в одну строку, которые
Workbench собирает в связь по настройке связей.

## Три слоя

| Слой | Где | Что делает |
|---|---|---|
| Хранение | `app.springbootcrm.reports` (хост, typeId 9500) | справочник отчётов: схема, настройки, макеты, формы |
| Сборка запросов | `app.modules.sqlworkbench.querypack` | строка с несколькими запросами + связи → один SQL (CTE + JOIN) |
| Компоновка | `app.modules.dcs` | макет → выполнение → дерево итогов, расшифровка, выгрузка |
| Конструктор | `frontend/src/modules/dcs` | 10 вкладок: наборы, связи, поля, ресурсы, параметры, настройки, макеты, формы, результат, форма отчёта |

Направление зависимостей строго одно: `dcs → sqlworkbench → app.springbootcrm`.
Хост не ссылается ни на один модуль.

## Как несколько запросов становятся связью

Отчёт хранит наборы данных **одной строкой** — служебная разметка спрятана в
SQL-комментарии `--#`, поэтому строка остаётся читаемой в любом редакторе:

```sql
--#query Deals
SELECT d.code AS code, d.amount AS amount, d.customer_id AS customer_id FROM deals d
--#query Customers
SELECT c.id AS id, c.name AS name FROM customers c
--#link Deals -> Customers LEFT ON customer_id = id
```

`QueryPackAssembler` собирает из неё один запрос: каждый набор становится CTE, а
связи — цепочкой JOIN'ов.

```sql
WITH qp_Deals AS (
SELECT d.code AS code, d.amount AS amount, d.customer_id AS customer_id FROM deals d
),
     qp_Customers AS (
SELECT c.id AS id, c.name AS name FROM customers c
)
SELECT Deals.amount AS Deals_amount, Customers.name AS Customers_name
FROM qp_Deals AS Deals
  LEFT OUTER JOIN qp_Customers AS Customers ON Deals.customer_id = Customers.id
WHERE Deals.amount >= ?
```

Тексты наборов попадают в запрос **без разбора**: модулю не нужен полноценный
SQL-парсер, и запрос пользователя остаётся ровно таким, каким он его написал.

Два решения здесь неочевидны и важны:

* **Имя CTE получает префикс `qp_`**, а к имени набора возвращается алиасом. Без
  этого набор, названный как существующая таблица (`Deals` при наличии `deals`),
  в H2 молча читал бы таблицу вместо выражения — и отчёт показывал бы данные не
  из того источника.
* **Набор без связей подключается `CROSS JOIN` с предупреждением.** Декартово
  произведение почти всегда означает забытую связь, но запрещать его нельзя —
  иногда оно нужно. Поэтому предупреждение, а не ошибка.

Этим же механизмом можно пользоваться и вне отчётов — через
`POST /api/sqlworkbench/query-pack/*`.

## Конструктор запроса внутри конструктора отчёта

Набор данных — обычный SELECT, а визуальный конструктор для него уже есть в
Workbench'е. Во вкладке «Наборы данных» монтируется **тот же самый** компонент
(`StatementEditor`), а не его копия: копия неизбежно разошлась бы с оригиналом —
ссылочный режим, соединения, объединения и подзапросы пришлось бы поддерживать
дважды.

Стыковка точна в двух местах:

* `statementToSql` отдаёт текст **без подстановки параметров** (инлайном занимается
  `buildExecutableSql`, здесь он не нужен). Поэтому `&Имя`, набранное в условии
  конструктора, доезжает до компоновщика макета и связывается параметром схемы —
  синтаксис у обоих один и тот же;
* дерево конструктора хранится в самом наборе (`dataSet.builder`), а в упакованную
  строку уходит только сгенерированный SQL. Строка остаётся читаемой и исполнимой, а
  запрос можно открыть и править дальше мышью.

Правка SQL текстом отвязывает набор от конструктора: разобрать произвольный SQL
обратно в дерево нельзя, и делать вид, что можно, было бы хуже, чем сказать об этом
прямо. Рядом — кнопка «Preview data»: набор исполняется отдельно, со связанными
параметрами, чтобы увидеть, что запрос вернул не то, на двадцати строках, а не на
дереве итогов, где ошибка источника выглядит как странные цифры.

## Конвейер компоновки

1. **Компоновщик настроек** накладывает пользовательские настройки на настройки
   отчёта (и вариант отчёта, если выбран). `null` — «не трогать», поэтому форма,
   меняющая один параметр, не затирает структуру, заданную автором.
2. **Сборщик использования** обходит настройки и раскрывает выражения ресурсов и
   вычисляемых полей, определяя, какие колонки наборов вообще нужны запросу.
3. **Компоновщик макета** строит SQL: пакет → CTE + JOIN, отбор → `WHERE` с
   bind-параметрами, и решает, где считать агрегаты.
4. **Исполнение** — через `QueryService` Workbench'а (только SELECT,
   `PreparedStatement`, read-only датасорс хоста).
5. **Процессор компоновки** строит дерево: вычисляемые поля, ресурсы на каждом
   уровне, кросс-таблицы, условное оформление, данные расшифровки.

### Где считаются итоги

Если все ресурсы — простые сворачиваемые агрегаты, в структуре нет детальных
записей, в выводе нет вычисляемых полей и весь отбор ушёл в `WHERE`, агрегацию
делает СУБД (`GROUP BY` по измерениям), а процессор сворачивает готовые итоги вверх
по иерархии. Иначе запрос отдаёт детальные строки и всё считает процессор.

Итог на каждом уровне — это **вычисление выражения над записями уровня**, а не
накопление. Поэтому ресурс `Сумма(Продажи.Сумма) / Сумма(Продажи.Количество)` на
итоге даёт правильное значение, а не сумму частных.

### Безопасность

Ни одно пользовательское значение не попадает в текст SQL: значения отборов
подставляются маркерами `&_fN`, параметры схемы — именами `&Имя`, и финальный
проход меняет все маркеры на `?` слева направо, собирая значения в том же порядке.

## Конструктор отчёта

Открывается из раздела «Отчёты» (справочник, typeId 9500) — вкладки повторяют
конструктор схемы 1С:

* **Наборы данных** — запрос каждого набора **визуальным конструктором или текстом**,
  метаданные полей (заголовок, роль, тип, доступность в отборе/группировке/порядке),
  автозаполнение полей по метаданным результата, предпросмотр данных набора,
  редактор упакованной строки целиком;
* **Связи** — настройка соединений с живым предпросмотром собранного SQL;
* **Вычисляемые поля** и **Ресурсы** — редактор выражений с проверкой на сервере и
  палитрой полей и функций;
* **Параметры** — типы, значения по умолчанию, списки доступных значений;
* **Настройки** — дерево структуры (группировки, кросс-таблицы, диаграммы),
  выбранные поля, отбор, порядок, условное оформление, параметры вывода;
* **Макеты** — сетка ячеек с подстановкой `[Поле]`;
* **Формы** — визуальный построитель форм отчёта;
* **Результат** — формирование, расшифровка по клику, выгрузка в XLSX/CSV;
* **Форма отчёта** — отчёт глазами пользователя: форма из вкладки «Формы»,
  наполненная живыми контролами.

## Что реализовано не полностью

* иерархические группировки строятся плоскими (схема не описывает поле-родителя) —
  движок сообщает об этом в предупреждениях;
* макеты применяются на выводе для областей «Шапка отчёта» и «Подвал»; области
  «Группировка» и «Детальные записи» рисует автоматический вывод;
* расчёт остатков по ролям полей, дополнение периодов, вложенные схемы и экспорт в
  PDF не реализованы.

Подробности — в [README модуля](backend/src/main/java/app/modules/dcs/README.md).

## Отключение и удаление

```yaml
dcs:
  enabled: ${DCS_ENABLED:true}   # false — раздел отчётов исчезает
```

Модуль требует включённого Workbench'а (`sqlworkbench.enabled=true`): условие
включения проверяет обе property сразу. Порядок удаления описан в README модуля;
справочник отчётов при этом остаётся работоспособным JSON-каталогом.
